CUSTOMER INCIDENT RESPONSE · SOC 2-ALIGNED OPERATING EVIDENCE

One escalation path. Explicit evidence. No invented SLA.

This workflow separates security vulnerability disclosure from customer production incidents, defines the minimum evidence required for triage, and records the communication boundary for enterprise customers. It is operational guidance, not a contractual response-time commitment.

Report through the correct channel

SECURITY VULNERABILITY

security@cyberdudebivash.com

Use for suspected vulnerabilities, unauthorized access, credential exposure, security-control bypass, or responsible disclosure. Follow Security Disclosure and security.txt.

CUSTOMER PRODUCTION INCIDENT

contact@cyberdudebivash.in

Use for customer-facing service degradation, API delivery failure, integration failure, entitlement/access issue, or CTI delivery disruption. Do not send API keys, bearer tokens, passwords, or other secrets.

Minimum incident evidence

Identity & scope
Organization, authorized contact, customer tier/tenant identifier where applicable, affected product or endpoint.
Time
First observed UTC timestamp, last observed UTC timestamp, and whether the condition is ongoing.
Technical evidence
Request ID/correlation ID if available, HTTP status/error code, sanitized logs, affected integration, expected behavior, actual behavior.
Business impact
Describe operational effect without exaggeration: blocked ingestion, stale feed, failed download, unavailable endpoint, or other measurable impact.
Secret handling
Redact credentials and sensitive tokens. If a credential may have been exposed, rotate/revoke it through the approved customer process rather than attaching it to the incident.

Severity used for triage

SEV-1 · Critical
Confirmed or strongly evidenced compromise, active unauthorized access, material cross-tenant exposure, or widespread production unavailability affecting critical customer use.
SEV-2 · High
Major customer-impacting degradation, repeated authenticated API failure, significant CTI delivery disruption, or security control failure without evidence of broad compromise.
SEV-3 · Standard
Limited degradation, isolated integration defect, non-critical data-quality issue, documentation mismatch, or recoverable customer workflow problem.
Classification rule
Severity is based on evidence and impact. A customer may state perceived urgency, but final operational classification should not be inferred from subject-line wording alone.

Lifecycle and evidence trail

1 · Intake
Capture reporter, timestamp, scope, sanitized evidence, affected service, and requested contact path.
2 · Triage
Validate reproducibility/current state, classify security-vs-service ownership, assign severity, and identify containment or customer workaround if supported by evidence.
3 · Containment
Apply the minimum safe change needed to stop active impact. Emergency action must preserve an auditable change record.
4 · Remediation
Implement the production fix, regression coverage, security validation, and release certification appropriate to the affected path.
5 · Verification
Verify the exact production surface, customer journey, and any affected machine-readable artifact or API endpoint.
6 · Closure
Record verified resolution, residual risk/limitations, customer-visible outcome, and follow-up actions. Material incidents should produce a concise incident review when appropriate.

Customer communication boundary

No public response-time guarantee is created by this page. Response objectives, escalation windows, service credits, support hours, notification duties, regulatory obligations, and customer-specific communication requirements apply only where explicitly executed in contract or order terms.
