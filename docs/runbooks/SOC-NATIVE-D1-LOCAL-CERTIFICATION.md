# SOC Phase 15 — native Wrangler local D1 admission and migration certification

**Status:** automated local-only CI rehearsal, **not** production acceptance.

## What this tests

Phase 14's quota ledger and atomic admission command passed ordinary SQLite and Jest mocks. This harness runs the actual installed Wrangler D1 local engine against the full current migration set, then invokes the **exact** admission SQL exported by the production source service.

```powershell
npm ci --legacy-peer-deps --ignore-scripts
node --test tests-js/soc-native-d1-local-certify.test.js
node scripts/soc-native-d1-local-certify.cjs
```

Its autogenerated Wrangler configuration uses a fixed synthetic database name `soc-native-offline-certification`, a fake local database UUID, **no assets, services, routes, production domain, Worker secrets or customer identifiers**, and a unique temporary persistence directory. Every CLI D1 invocation explicitly includes `--local`, its private `--config` and `--persist-to`; Cloudflare account environment credentials are excluded and Wrangler telemetry is suppressed.

The harness exercises: the 0001–0016 sequential SQL migration chain, creation of `soc_evidence_read_windows`, admission increments 1 and 2, rejection at a two-read limit, another tenant/connector's distinct budget, refusal after connector PAUSED, refusal after tenant SUSPENDED, and cleanup. It exits nonzero on a failing migration or inconsistent D1 result. No cloud resources, billing, customer records or public routes are created.

## What it cannot certify

- It does **not** call `--remote`, use a production database, confirm replica/primary routing under `withSession('first-primary')`, simulate Worker fetch routing, test concurrency across regions, check actual Cloudflare D1 quotas or apply migrations to the live account.
- Fake offline tenant/connector records are used only in temporary local D1.
- It cannot certify EDR/SIEM provider ownership, the source byte custody chain, IDP or customer legal consent, incident operations, tenant isolation outside these SQL checks, readiness for the new `soc.` hostname or revenue.
- Production migration 0009–0016 may encounter existing data and later business schema differences that are not represented by a fresh local database. Require a separate authorized anonymized schema/data inventory, rollback rehearsal and staged Cloudflare deployment.

## P0 release control

The harness belongs to the existing GitHub Build Verification job and runs before the full E2E, governance, performance, resilience and coverage chain. Its failure is an explicit NO-GO: never suppress it, substitute pure SQLite pass counts or run a remote migration to work around the local result.

The source PR is review-only; `main` pushes may trigger the Cloudflare production workflow. Approve deployment separately only after runtime, legal, operational and commercial gates pass.
